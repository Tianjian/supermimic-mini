# 全局评审：算力/显存限制到底限制了我们的什么？

> 日期：2026-11-15
> 问题：是算力和显存限制导致实验设计受限，从而难以复现 WM-BPTT 的提升吗？
> 结论先行：**算力限制了我们能跑的"规模"，但解释不了我们观察到的"负结果"。真正让我们失败的是三处为省算力做的简化——而它们恰好移除了让 BPTT 稳定的关键部件。显存从来不是瓶颈（我们只用了 3/16 GB）。**

## 二、但显存从来不是瓶颈

这一点必须说清楚，因为很容易误以为是卡太小：

- 我们跑论文同款 **2048³ 的 WM**（容量一致）；
- AC 循环实测显存占用 **2–3.6 GB / 16 GB**（连零头都没用满）；
- 论文里"80 GB 才够"的地方是 **H=128**，我们跑 H=16/32 完全够；
- 开源复现的地板是 **24 GB（4090）**，而我们只用了 3.6 GB。

**所以"显存不够"这个解释不成立。** 真正的限制是 **wall-clock**（4096 环境的 CPU 仿真 + 单卡吞吐）。

---

## 三、算力限制解释了"规模"，解释不了"负结果"

这是本评审最重要的判断，证据有三：

### 证据 1：崩塌发生在第 10–20 轮

如果失败是"样本不够、学得太慢"，应该表现为**提升缓慢**。实际是**在 10–20 轮内从 0.38 崩到 0.07**。再多的算力跑同一份代码，只会让崩塌更彻底。

### 证据 2：WM 精度提升 3.2× 只把伤害从 −80% 挪到 −69%

我们把 on-policy NSE32 从 4.51 降到 1.02（−77%，已经是很大的工程质量提升），BPTT 依然崩。**说明不是"模型还不够准"这么简单**。

### 证据 3：夹具（约束动作）立刻止崩

同一份 WM、同一个底座，只把想象动作夹在锚点附近，崩塌就从 −80% 变成 −0.8%。
**这是方向性问题，不是样本量问题。**

## 四、真正让我们失败的三处"为省算力做的简化"

对照论文的公式，我们的实现有三处**不是硬件强制的、但很关键**的偏离：

### D1. 我们把 critic 的 bootstrap 从梯度里 detach 了 ⚠️

论文的式（policy-obj）：

$$\hat J(\theta)=\mathbb E\Big[\sum_{t=0}^{H-1}\gamma^t\hat c_t\,\hat r_{t+1}\;+\;\gamma^H\hat c_H\,V_\psi(\hat s_H,g_H,\xi)\Big]$$

并且明确写 **"BPTT computes a first-order gradient ∇θĴ through the H imagined steps"**——也就是**从 V(ŝ_H) 回传到策略**。

我们的代码：

```python
J = J + disc * v_last.detach()      # ← bootstrap 被 detach
```

**后果**：H 变成一道硬墙。策略只能看到 16 步（0.32 秒）内的回报，第 16 步之后的一切与它无关。论文用 critic 把视野延伸到 H 之外，这正是它"短视野也能做长程信度分配"的关键。我们把它关掉了。

**这不是算力限制**——把 `.detach()` 去掉不增加任何计算量（只是多一条反向边）。

### D2. 我们没有 survival weight ĉ_t，也没有终止头 ⚠️

论文的 ĉ_t 是由世界模型预测的终止概率 `d̂_t = d_ω(ŝ_t, g_t)` 算出的软存活权重，它把"快要摔倒"的未来的回报**乘到接近 0**，从而让策略学会避免摔倒。

我们的 `reward8` **完全没有终止项**：想象 rollout 永远不终止，16 步的跟踪奖励照常累加。

**后果**：WM 可以预测"这 16 步跟踪得很好"，而真值里机器人正在摔倒。策略于是在优化一个**不会摔倒的幻觉**。这与我们观察到的崩塌形态高度吻合。

**这也不需要算力**——加一个 64×64 的终止头是几万参数。

### D3. WM 不是持续在线的 ⚠️

论文 Algorithm A.1：**每次迭代都**用当前策略采数据、更新 WM、更新策略——三者交替。

我们做的是：离线 WM 训到 100k → 一次性采 on-policy 数据 → 微调 6000 步 → 然后跑 60 轮 BPTT，**期间 WM 冻结、数据不再更新**。

所以 BPTT 期间策略在漂移，而 WM 停在原地，两者逐渐脱节——**这正好解释了"it20 达峰、之后衰减"的形态**。

这一项**部分**受算力限制（持续采集需要吞吐），但本机 CPU 采 100k 只要 8 分钟，做 3–5 轮交错完全可行。

## 五、其他"确实是算力/数据所限"的项

| 项 | 是否受限于算力 | 说明 |
|---|---|---|
| 迭代次数 60 vs 320k | ✅ 是 | 本机跑满需 33 天 |
| 想象样本 6×10⁴ vs 4×10¹⁰ | ✅ 是 | 差 68 万倍 |
| 并行环境 64 vs 4096 | ⚠️ 部分是 | CPU 无 Warp；但 64 也是我们自己选的（B=64 每次要 64×10 次环境热身，为了迭代快） |
| WM 在线循环 | ⚠️ 部分 | 采集够快，但交错会拖长单次实验 |
| BONES-SEED 129k 动作 | ❌ 不是算力 | 是**许可 + 存储**（gated + 3.5 TB） |
| 单卡单种子 | ❌ 不是算力 | 是**实验设计习惯**（后来补到 10 种子才纠正） |
| 策略 batch 64 | ❌ **不是** | 显存只用 3.6/16 GB，B=512 也放得下 |

## 六、所以，如何回答你的问题

**部分成立，但不是主因。**

- ✅ **成立的部分**：算力（wall-clock，不是显存）确实让我们**无法跑论文的完整规模**，也无法做"每轮在线"的完整循环，更没法做大规模超参搜索。这限制了实验的**广度与统计强度**。
- ❌ **不成立的部分**：算力**不是** BPTT 变差的原因。崩塌是**方向性**的（10–20 轮内发生、夹具立刻能止住、模型准 3 倍也没用）。
- ⚠️ **真正的教训**：我们为了在有限算力内快速迭代，**简化掉了三个"不花算力但很关键"的部件**——可微 bootstrap、终止头/survival weight、持续在线循环。**这些恰好是论文用来让短视野 BPTT 稳定的东西。**

一句话：**不是"算力不够所以做不出来"，而是"为了省算力做的简化，正好拆掉了让 BPTT 稳定的三个零件"。**

---

## 七、据此修正的优先级（比原 M1–M4 更根本）

原来的 M1–M4 都在"调夹具/正则"这一层，属于**绕过**问题。下面三项属于**修复**问题，而且都不贵：

| 优先级 | 修复 | 成本 | 理由 |
|---|---|---|---|
| **P0** | **去掉 `.detach()`**，让 ∇θ 穿过 V(ŝ_H) | 改 1 行 + 30 min 验证 | 恢复论文的长程信度分配；零额外算力 |
| **P1** | **加终止头 + survival weight ĉ_t** | ~1.5 h | 让"快要摔倒"的未来被折现掉；这是崩塌最可能的直接原因 |
| **P2** | **交错的在线循环**（每 20 轮采 20k 新数据 + 微调 WM） | ~1 h | 消除"策略漂移、WM 停在原地"的脱节 |

之后再回到 M2（BC 锚定软正则）——它作为**辅助正则**仍有价值，但不该是主线。

---

## 八、一个诚实的补充

即使 P0–P2 全部修好，我们**也不可能**在 16 GB / 无 CUDA 的机器上复现论文的 0.82。规模差 68 万倍，这个差距是硬的。

但"能不能让 BPTT 在教师底座上稳定产生 +5% 而不是 −80%"是**另一个问题**，而它不取决于算力——取决于上面三个零件。
